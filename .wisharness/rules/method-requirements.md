# 需求澄清与领域语言

需求有歧义或关键取舍未定时使用；通用约束见 [core](core.md)。

- 先查已有需求、契约和代码，并从可用资料、工具和相关入口补齐上下文。先解决前置问题；上下文足够时由 Agent 判断行为、边界与取舍并继续，不要求用户替 Agent 设计方案。已确认的决定不重复询问，不追加额外确认。
- 只有影响结果且无法自行获得的信息缺失时才询问，问题聚焦缺失的事实或上下文，说明影响并给出建议，不把方案选择题当作上下文问题。仅暂停依赖该信息的工作；已有证据足够的部分继续执行。
- 沿用项目领域术语，用反例检查同名异义；当前实现不能代替预期行为。术语与契约冲突时按用户目标、明确约束和证据处理，记录判断依据；确实缺少决定性上下文时按上一条询问。推断和假设须明确标注，不写成用户已确认的事实，不能借推断覆盖明确要求或扩大授权。
- 需要长期保留的术语和重要取舍写入项目已有文档，不额外规定文件名或文档类型。
- 结论写回已有需求、spec/plan 或 Change，保留验收及剩余问题；复杂需求的文档存放见[设计与任务拆分](method-design-planning.md)，未启用团队协作不强制建 Change。
