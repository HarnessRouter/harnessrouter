# 设计与任务拆分

复杂功能、接口调整或迁移时使用；通用约束见 [core](core.md)。

- 按 [core 的复杂度判断](core.md#按任务需要组织工作)，在修改生产实现前分别记录 spec（行为、边界与验收）和 plan（方案、步骤与验证）；任务范围扩大时先补齐再继续实现。已有对应文档直接复用；新建时沿用项目目录约定，无约定则用 `docs/changes/<change-id>/spec.md` 和 `plan.md`，同一需求复用目录。简单需求不强制建文档。
- 编写或更新 spec、plan 前，必须先完整读取并参考 [spec 模板](../templates/spec.md) 和 [plan 模板](../templates/plan.md)，再按模板填写。模板缺失或不可读时先报告并修复路径，不得跳过。
- 沿用模板结构填写各项内容，不适用项说明原因。复用已有文档时在原文中补齐，正文只维护一处，其余位置用摘要和准确引用。
- spec/plan 的要求不依赖团队协作开关，不新增审批节点。命中已启用的团队协作规范的共享变更条件时，必须创建或复用 `change-record.yaml`，状态、实际验证证据与剩余事项统一写入该文件，plan 只引用；不得以已有 spec/plan 或任务正文替代。仅未要求独立 Change 且没有已有任务或 Change 时，才将执行结果记在 plan。交付前逐项对照模板检查完整性。
- 以调用者负担和已有架构约束判断接口；不为想象中的扩展引入抽象，不将设计建议变成未经授权的重构。
- 按可验收行为纵向拆分，注明验收、真实阻塞关系和验证入口；复用已有计划，不另建进度表。
- 跨模块迁移按兼容新增 → 分批迁移 → 删除旧实现推进。每批保持必要验证通过；共同集成前不宣称整体可交付。
- 本方法不自动授权多 Agent 委派。已授权并行时明确责任和隔离边界，合并后仍须验证整体行为；协作记录遵循已启用的团队规范。
