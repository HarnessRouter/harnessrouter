# UI 对齐：视觉契约驱动验收

修改前读取可用的设计文档、截图、原型、组件规范或用户指定对标产品，记录来源、版本、页面及状态；明确要求优先，不从当前实现的缺陷反推目标契约。
无设计资料时，Agent 根据用户目标、项目风格、已有组件与可用性要求制定本次视觉目标，记录依据并直接实施；普通布局、间距、颜色和响应式取舍由 Agent 判断，不要求用户逐项确认。仅影响结果且无法自行获取的关键上下文缺失时询问，并附建议。

## 设计到验收

用 `.wisharness/templates/visual-contract.md` 记录结构、内容、交互状态、可访问性、几何、颜色圆角、响应式断点及关键截图。沿用项目实际 UI 测试入口，不指定框架或宿主。
实现前将可自动验证目标写成 UI 验收测试，运行并确认因未对齐而失败；其余由 Agent 使用截图和真实交互检查并记录结果，不因缺少自动断言而默认要求人工验收。优先按可访问角色、名称、可见文本定位，覆盖错误、空状态、加载、恢复及关键尺寸。

## 判定

- 结构、可访问性、可操作性、内容溢出及关键断点错误为硬失败，功能 E2E 通过不等于视觉对齐。
- 已有契约或 capabilities.settings.ui.tolerancePx 时遵循其约束；无数值时由 Agent 按目标平台、字体、渲染环境和改动风险选择验收方法，需要量化时在实现前制定有依据的容差或截图阈值，否则使用明确的布局、可读性与交互检查项。不仅因未配置数值就阻塞或标未评估，不强制用户提供像素值，不预设适用于所有项目的固定阈值。
- 在验收标准内、不影响使用的轻微差异由 Agent 判断并按需记 advisory；违反明确契约或超出已定阈值时修复并复验，不为让结果通过而事后放宽标准。若证据表明原标准不适用，记录原因并重新建立独立验收依据；不得覆盖用户或项目的明确要求。
- 缺历史截图不自动阻塞：Agent 可依据实现前确定的目标建立目标平台基线，并实际检查关键状态，不能仅保存当前截图就判通过。未能在目标平台实际检查或验证时记 not_evaluated，说明限制与补验方式，不宣称该平台视觉验收或相关发布门禁通过。

## 证据

保存结构化报告、独立可查报告、关键状态截图及哈希，注明设计来源、提交、平台、视口和测试命令。目录、报告格式沿用项目工具；原始证据不含秘密，按项目文档生命周期保存，Change 仅链接结论与证据。
分别报告功能、视觉、advisory 和未评估结论；仅项目明确要求人工验收或真实访问限制需要用户参与时列人工待审，不默认增加人工审批。必需门禁未通过不得宣称 UI 完成。
